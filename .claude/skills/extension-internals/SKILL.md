# AgentCRM modules and extensions — contributor notes (this repo)

This skill covers what is specific to working **inside** the AgentCRM repository. Authoring itself (`defineModule` / `defineTheme`, recipes, build config, `agentcrm ext new|check|pack|install`) is documented in:

- the distributed authoring skill: [`plugin/skills/agentcrm-extensions/SKILL.md`](../../../plugin/skills/agentcrm-extensions/SKILL.md) and its references (`runtime-api.md`, `module-recipes.md`, `theme-recipes.md`, `testing.md`);
- [`docs/extensions.md`](../../../docs/extensions.md), [`docs/creating-a-module.md`](../../../docs/creating-a-module.md), [`docs/creating-a-theme.md`](../../../docs/creating-a-theme.md), [`docs/runtime-api-reference.md`](../../../docs/runtime-api-reference.md), [`docs/modules.md`](../../../docs/modules.md), [`docs/appearance.md`](../../../docs/appearance.md);
- the API contract of record: [`types/agentcrm-runtime.d.ts`](../../../types/agentcrm-runtime.d.ts) (shipped in the npm package, copied into every project by `ext new`).

Read [CLAUDE.md](../../../CLAUDE.md) ("Customisation: modules, extensions, appearance") and [AGENTS.md](../../../AGENTS.md) first. Don't commit unless asked. For the CLI, MCP, skills, Hermes, releases and QA runs see [`agent-cli-internals`](../agent-cli-internals/SKILL.md).

## Where things live

| Piece | Source | Notes |
|---|---|---|
| Built-in modules | `src/features/<id>/index.ts` with `module: moduleMeta("<id>")`, catalog `BUILTIN_MODULES` in `src/core/modules.ts` | `src/ops/modules.test.ts` keeps `FEATURES` ⇔ `BUILTIN_MODULES` identical. State: doc `config/modules` (`disabled[]`, `config{}`), ops in `src/ops/modules.ts` |
| Extension runtime | `src/extensions/` — `api.ts` (versions, limits, specifiers), `package.ts` (manifest / ZIP, DOM-free, shared with the CLI), `runtime.ts` (`installRuntime`, `runtimeApi`), `loader.ts` (`syncExtensions`, safe mode), `registry.ts` (`activateExtension` / rollback), `nodeImport.ts` (CLI) | `runtime.ts` is the first import of `src/main.tsx` |
| Runtime stubs | `public/runtime/*.js` → `dist/admin/runtime/` | `agentcrm-runtime.js` is hand-written; the others are GENERATED by `npm run gen:runtime-stubs` (`scripts/gen-runtime-stubs.mjs`) — rerun after upgrading react, react-dom, react-i18next or lucide-react |
| Import map | `index.html` | one entry per `RUNTIME_MODULES` specifier (`src/extensions/runtime.test.ts` checks it) |
| Stored extensions | collection `extensions` (`ExtensionDoc`), ops in `src/ops/extensions.ts` | encrypted with the dataset on file backends; Firebase splits docs over `extensionChunks` (`assembleExtensionDocs` in `src/data/firebase.ts`) |
| Shell | `src/app/featureRegistry.ts` (`registerExternalFeature`, `connectModuleState`, `useSlot`) | components read slots with `useSlot(name)` so they re-render when modules toggle |
| Themes / appearance | `src/appearance/` (`themes.ts` `registerExternalTheme`, `schema.ts` `resolveAppearance`, `apply.ts`), ops `src/ops/appearance.ts`, UI `src/features/customize/` | resolution: `DEFAULT_APPEARANCE` ← enabled theme's values ← stored doc |
| Examples | `external/modules/hello-module`, `external/modules/sales-goals`, `external/themes/midnight` (+ `external/vite.extension.ts`, `external/tsconfig.base.json`) | `npm run build:examples` (not part of `npm run build`) → `dist/extensions/<id>-<version>.zip`; `dist/` is git-ignored, nothing to commit |
| CLI | `agent/commands/ext.ts`, `agent/ops/extScaffold.ts`, `extCheck.ts`, `extPackage.ts`, `extensions.ts` (session loading, `runtimeDir()`) | stub lookup: `$AGENTCRM_RUNTIME_DIR` > `dist/admin/runtime` > `public/runtime` (also next to the CLI file) |

Built-in features import `src/` directly; **extensions only see `@agent-crm/runtime`** and the six shared libraries. An extension that needs something new means a new runtime export, never a deep import.

### A new built-in module

1. Catalog entry in `BUILTIN_MODULES` (`src/core/modules.ts`): id, label, summary, category, `dependsOn?`, `objects?`, `settingsSection?`.
2. `module: moduleMeta("<id>")` in the feature's `index.ts`, and the feature in `src/features/index.ts`.
3. i18n keys `customize:modules.catalog.<id>.{name,description}` in `src/features/customize/i18n/{en,fr}.json` (`src/i18n/parity.test.ts` checks en ⇔ fr).
4. The id becomes reserved for extensions automatically (`RESERVED_EXTENSION_IDS` in `src/extensions/package.ts` is derived from the catalog). Update `docs/modules.md` and the id list in `docs/extensions.md`.

## Extending the runtime API

Adding (or changing) something extensions import from `@agent-crm/runtime`:

1. **`src/extensions/runtime.ts`** — add it to `runtimeApi`.
2. **`public/runtime/agentcrm-runtime.js`** — `export const X = R.X;` (bundles import this stub through the import map, or through the loader's specifier rewrite to absolute stub URLs).
3. **`types/agentcrm-runtime.d.ts`** — declare it with self-contained types (only `react` and `lucide-react` types may be imported; domain types are restated).
4. **`src/extensions/runtime.test.ts`** — value-export lists of `runtimeApi`, the stub and the `.d.ts` must be identical; the compile-time `_curatedFromReal` assignability and the `Mutual<Real, Curated>` checks catch signature drift — add a `Mutual` line for any new shared interface. Run `npm run typecheck` and `npx vitest run src/extensions/runtime.test.ts`.
5. **Version** — a new export / optional field is a **minor** bump of `EXTENSION_API_VERSION` in `src/extensions/api.ts`; raise `EXTENSION_MIN_API_VERSION` only on a breaking change (older bundles stop loading — avoid it). Also update the version quoted in `docs/runtime-api-reference.md` and `docs/extensions.md` ("today `1.0.0` … `1.1.0`"), and the examples' `apiVersion` (manifest **and** the default export) if they use the new export. `ext new` and `ext check` read the constants directly.
6. **Docs + skill** — `docs/runtime-api-reference.md` (`scripts/docs.test.ts` fails when an export or exported type is missing), `plugin/skills/agentcrm-extensions/references/runtime-api.md`, then `npm run hermes:build`. The list of runtime exports in CLAUDE.md too.

**Optional domain fields can't drift any more.** Assignability alone lets an optional key added to `src/core/types.ts` (or a new optional prop on a UI kit component) pass without touching the `.d.ts`; since 0.12.1 the `_MutualChecks` of `runtime.test.ts` use `Same<Real, Curated>` (mutual assignability **and** identical key sets), so an optional key added to a checked type (`CrmRecord`, `FieldDef`, `CrmUser`, `FieldValueProps`, `SchemaSpec`, `SyncReport`…) fails `npm run typecheck` until `types/agentcrm-runtime.d.ts` restates it. The check is shallow: add a `Same<…>` line for a new nested contract type. A new op module must be re-exported by `src/ops/index.ts` to reach the runtime's `ops` (`schemaApply.ts` and `syncRecords.ts` are, since API 1.1.0); typing it in `RuntimeOps` is a minor `EXTENSION_API_VERSION` bump.

A new **bare specifier** (another shared library) additionally needs: `RUNTIME_MODULES` in `src/extensions/api.ts`, a stub in `public/runtime/` (+ an entry in `scripts/gen-runtime-stubs.mjs`), the import map in `index.html`, `RUNTIME_EXTERNALS` in `external/vite.extension.ts` and `RUNTIME` in `scripts/build-examples.mjs`. The scaffold and `ext check` derive theirs from `RUNTIME_SPECIFIERS`. Prefer adding a function to `@agent-crm/runtime` instead.

## Package rules (keep the admin and the CLI in agreement)

- `src/extensions/package.ts` is the only validator, used by the admin's install dialog, `src/ops/extensions.ts` and every `ext` command: manifest keys (unknown keys rejected), id pattern `EXTENSION_ID_RE`, `SEMVER_RE`, `isCompatibleApiVersion`, `EXTENSION_LIMITS` (bundle 1.5 MB, style 256 KB, manifest 16 KB, ZIP 4 MB), bare imports limited to `RUNTIME_SPECIFIERS`. A new rule goes there, with a test in `package.test.ts` and a hint in `agent/ops/extCheck.ts` when an author can hit it.
- `activateExtension` (`src/extensions/registry.ts`) must roll back everything on error (feature, AI tools, automation actions, style, `register()` disposers). The bundle's `default.id` must equal the manifest id.
- `syncExtensions` never throws and is serialised; a failing extension becomes `status: "error"` and a note, never a broken admin or CLI command.
- Installing runs code with admin rights: admin only, explicit trust in the UI, a plan in the CLI, never an AI tool. `ext install` trial-loads the bundle in a throw-away CRM first (`--force` skips it).

## AI tools and automation actions from extensions

- `registerAiTool` (`src/ai/tools.ts`): snake_case, unique across built-ins and extensions. Every front door lists `listAiTools()`; MCP re-syncs extensions after a mutating tool.
- `registerAutomationAction` (`src/ops/automations/extensionActions.ts`): action `{ type: "extension", action: "<moduleId>.<name>", params }`. Validation refuses unknown / non-applicable actions; a run whose action is no longer registered fails with "not available". The automation editor lists registered actions. Tests: `src/ops/automations.extension.test.ts`.
- CLI sessions load enabled extensions (`agent/ops/extensions.ts`) only when some are enabled, so hooks and automation actions run in `automations run` from the cron.

## Checks before handing over

```bash
npm run typecheck
npx vitest run src/extensions src/ops/extensions.test.ts src/ops/modules.test.ts scripts/docs.test.ts
npx vitest run src/extensions/e2e.test.ts agent/e2e-customize.test.ts   # builds the examples / a scaffold with Vite
npm run build:examples && node dist/agent/agentcrm.mjs ext check dist/extensions/<id>-<version>.zip
npm run build && npm run check:skills && npm run check:hermes           # when skills or the CLI changed
```

`npx vite build --config vite.agent.config.ts` rebuilds only the CLI (enough to run `ext check` after changing `agent/` or `src/extensions/`). Try a changed extension in the admin in light and dark mode, in French, and as admin / member / viewer, without `npm run dev` if the owner is running it (see the QA notes in `agent-cli-internals`).
