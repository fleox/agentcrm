# Firebase backend — contributor notes (this repo)

Read [CLAUDE.md](../../../CLAUDE.md) ("Other backends", "Images & attachments") first. User-facing guide: [docs/firebase.md](../../../docs/firebase.md); files: [docs/files.md](../../../docs/files.md); lead inbox: [src/features/forms/INBOX.md](../../../src/features/forms/INBOX.md). Don't commit unless asked. Never run `agentcrm install` against the maintainer's own Firebase project.

## The threat that shapes everything

The Firebase web config (`apiKey`…) is public — it sits in `config.js` — so **anyone can create a Firebase Auth account on the project**, and with Email/Password enabled, with *any* address. Signing in proves nothing: authorization comes only from Firestore data the rules control, and only **verified** addresses count. The admin's own checks (`assertCan` in `src/ops/`) are UX in Firebase mode; the rules are the real access control. Never add a path where an account grants itself a role.

## Who gets in

`ensureUserRecord` (`src/data/firebase.ts`) runs at each sign-in:

1. Existing `users/{uid}` → its role.
2. Unverified address → `FirebaseAccessError("unverified")` (the access screen offers "I've verified it" and a resend button).
3. Try to create the record as **admin**: only the bootstrap admin passes (email pinned in the rules' `bootstrapAdminEmail()`, never in `config.js`).
4. Else read `invites/{lower-case email}` and create the record with the invitation's role (`replaces: <placeholder userId>` when the admin pre-created the user).
5. Else try as **member**: passes only when the sign-up mode allows it (`open`, or `domain` with a matching verified address).
6. Else `FirebaseAccessError("notInvited")`.

- Invitations are mirrored by the store from the users an **admin** writes (`inviteOps`, ids through `emailKey` = lower-case). Non-admin batches never include them (the rules would fail the whole batch).
- Placeholder users: an admin adds someone in Settings → Users before they ever signed in; when they join, `replaces` hides the placeholder and an admin's browser rewrites owners / assignees / `user` fields to the real uid (`scheduleReconcile` → `reconcile`) and deletes the invitation.
- Users can change only their own `name` / `avatarUrl` (+ `updatedAt`); nobody changes their own `role`, `email` or `disabled`. `disabled: true` = no access at all.

## Sign-in methods

- `signInMethods?: ("password" | "google")[]` in the Firebase runtime config (`FIREBASE_SIGN_IN_METHODS`, `src/lib/runtimeConfig.ts`). Not secret.
- Each method also has to be enabled in Firebase console → Authentication → Sign-in method, and the admin's domain added under Authorized domains, or sign-in fails there.
- **Password always works for the CLI**: credential type `firebase` = `{ email, password }` of a CRM admin (`agent/credentials.ts`); the CLI signs in like the login screen.
- New auth behaviour goes through the `FirebaseApi` interface (real adapter + memory fake) so `src/data/firebase.test.ts` can cover it.

## Rules: generated, not hand-written

The rules are code (`src/ops/firebaseRules.ts`), handed out by the setup wizard, Settings → Data backend and `agentcrm options --firebase-rules <admin email>` (Firestore rules, default sign-up `invite`). `docs/firebase.md` explains them; it is not a build input.

- Admin-write collections: `ADMIN_WRITE` (`objects`, `pipelines`, `forms`, `settings`, `config`, `extensions`); member CRUD: `MEMBER_WRITE` (`records`, `activities`); dedicated blocks for `users`, `invites`, `views`, `automations`, `automationRuns`, `files`, `extensionChunks`, `inbox`; everything else closed.
- **A new collection** (`COLLECTIONS` in `src/data/types.ts`) needs a rule here — `src/ops/firebaseRules.test.ts` fails until `RULED_COLLECTIONS` covers it — plus `crmRulesModel` in `memoryApi.ts`, the role table in `docs/firebase.md`, and scenarios in the emulator harness.
- Storage rules (`buildStorageRules`) read the role from Firestore `users/{uid}` (cross-service rules; the first deploy asks to allow it), cap the object size (`maxUploadMb`, default 100 MB) and the id pattern `^[A-Za-z0-9_-]{1,80}$`. Bytes need bucket CORS for the admin's origin (`buildStorageCors`, `gsutil cors set`).
- The lead inbox is the only public write: `validSubmission` bounds the shape with `INBOX_LIMITS` (form must exist, ≤ 60 fields, ≤ 10 meta keys, `createdAt` int within ±24 h). Keep `buildInboxSubmission` and the rule in step.
- **Changing the rules on released CRMs**: users must re-generate and re-publish them. Add a `changelog.json` action saying so (0.3.0 did, for `storage.rules` and the `files` collection) and update `plugin/skills/agentcrm-install/references/firebase.md` (+ `npm run hermes:build`).

### Testing the generated rules on the emulator

Run this after **any** change to `src/ops/firebaseRules.ts`. The harness in [`rules-test/`](rules-test/) bundles the generator straight from `src/` with esbuild (a Vite dependency in the repo's `node_modules`), so it always tests what users get:

- `test.mjs`: Firestore — bootstrap admin, strangers, invitations (case, roles, placeholders, forged `authUid`), unverified accounts, member / viewer permissions per collection, views, automations, files, extensions, the public inbox (shape, unknown form, stale date, size), revocation, closed default, and the `open` / `domain` sign-up variants.
- `storage.mjs`: Storage — read / write / delete per role, disabled users, size limit, unsafe ids, paths outside `files/`.

Prerequisites: Java 21+ for the emulators (`openjdk@21` from Homebrew on the maintainer's Mac), `npm install --legacy-peer-deps` at the repo root (esbuild), network for the first install. Its `.gitignore` covers `node_modules`, the lockfile and the emulator logs. The emulators listen on 127.0.0.1:8180 (Firestore) and :9299 (Storage), away from the defaults.

```bash
export PATH="/opt/homebrew/opt/openjdk@21/bin:$PATH"
cd .claude/skills/firebase-internals/rules-test
npm install --legacy-peer-deps
npm test     # firebase emulators:exec --only firestore,storage "node test.mjs && node storage.mjs"
```

The emulator prints `false for 'create' @ L…` / `PERMISSION_DENIED` lines for the expected refusals: read the final `N passed, 0 failed` lines (one for Firestore, one for Storage). Add a scenario for each new rule, including the refusal. Cross-service Storage rules only see the Firestore data of the `emulators:exec` project, so `storage.mjs` uses that project id.

## Securing or debugging a live CRM

1. `agentcrm doctor --site <alias>` (credentials, data access, hosted admin, `config.js` without secrets).
2. `agentcrm options --firebase-rules <bootstrap email> --json` (or Settings → Data backend for other sign-up modes); the **user** publishes the rules in the console or with `firebase deploy --only firestore,storage` — the CLI has no rights on the project.
3. `agentcrm users list --site <alias>`: look for unknown accounts, `users disable` them.
4. Test any change to the join flow with a **brand-new invited account**, not a reload of an existing session.
